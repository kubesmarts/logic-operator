= Deployment Overview
:description: What gets deployed when you install Logic Operator and how the components fit together.

Logic Operator is a Kubernetes operator that manages Open Workflow (OWS) workflows powered by Quarkus Flow.
It follows the standard operator pattern: a controller pod watches custom resources and reconciles the cluster state to match the declared spec.

== Installed Components

When you deploy Logic Operator, the following components land in your cluster:

`logic-operator-system` namespace::
The operator itself runs here as a `Deployment` named `logic-operator-controller-manager`.

Custom Resource Definitions (CRDs)::
Four CRDs are installed cluster-wide:
+
[cols="1,2"]
|===
|CRD |Purpose

|`LogicPlatform`
|Manages Data Index (GraphQL service) and Vector (log collection DaemonSet)

|`LogicFlowRuntime`
|Manages the Quarkus Flow Runner pod(s) and their configuration

|`LogicFlowDefinition`
|Stores an OWS 1.0.0 document and links it to a runtime

|`LogicFlowService`
|Exposes a workflow as an HTTP endpoint via an Ingress
|===

RBAC::
ClusterRoles and ClusterRoleBindings that allow the operator to watch and manage pods, deployments, services, ingresses, configmaps, secrets, and leases across all namespaces.

Webhooks::
Validating and mutating admission webhooks for `LogicFlowRuntime` and `LogicFlowDefinition`.
These are served by the operator pod and secured by cert-manager.
A `Certificate` and `Issuer` are created automatically.

== Architecture

The diagram below shows how the components relate at runtime.

----
  kubectl / CI                   Operator Pod (logic-operator-system)
       |                               |
       | apply LogicPlatform           | watches CRDs
       | apply LogicFlowRuntime        |
       |-----> kube-apiserver <--------|
               |       |              |
               |       | webhook TLS  |   cert-manager
               |       |<-------------|---[ Certificate ]
               |
               | reconcile
               v
         LogicPlatform:
         ├─ Data Index Deployment
         ├─ Vector DaemonSet
         └─ Ingress/Route

         LogicFlowRuntime:
         ├─ Deployment (hello-runtime)
         │  └─ Pod: quarkus-flow-runner
         │     ├─ /q/metrics  /q/health
         │     ├─ /q/flow/exec/<ns>/<workflow>/<version>
         │     └─ JSON logs (structured logging)
         │
         ├─ Service
         └─ Ingress --> hello.lvh.me

         Data Flow:
         quarkus-flow-runner (JSON logs)
           → Vector DaemonSet
           → PostgreSQL
           → Data Index (GraphQL)
----

The runner image tag controls capabilities:

* `quay.io/quarkiverse/quarkus-flow-runner:1.0.0-minimal` — stateless, no persistence, no structured logging
* `quay.io/quarkiverse/quarkus-flow-runner:1.0.0-standard` — PostgreSQL persistence, lease-based sharding, structured logging

== Prerequisites

All environments require:

* Kubernetes {k8s-min-version}+
* cert-manager (manages TLS for admission webhooks)

Local development additionally requires:

* KIND v0.20+
* Docker v17.03+
* kubectl v1.30+
* Go v1.26+ (to build the operator image)
* ingress-nginx (installed automatically by `make kind-create`)
