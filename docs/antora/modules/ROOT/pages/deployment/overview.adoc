= Deployment Overview
:description: How Logic Operator, its four custom resources, and managed workflow components fit together.

Logic Operator watches its custom resources and reconciles Kubernetes resources to match their
specifications. The CRDs are cluster-scoped definitions; each LogicPlatform, LogicFlowRuntime,
LogicFlowDefinition, and LogicFlowService object is namespaced.

== Installed components

The operator runs as a Deployment, typically in `logic-operator-system`. Installing the operator
also installs the CRDs, admission webhooks, and RBAC.

[cols="1,3",options="header"]
|===
|Custom resource |Managed behavior

|`LogicPlatform`
|Manages Data Index, optional Vector log collection, and optional Workflow Gateway resources.

|`LogicFlowRuntime`
|Manages a Quarkus Flow Runner Deployment and Service. When persistence is configured, it also
manages Lease coordination and runtime RBAC.

|`LogicFlowDefinition`
|Stores one OWS workflow document and creates a per-definition ConfigMap mounted by its runtime.

|`LogicFlowService`
|Creates an external workflow endpoint using Kubernetes Ingress, OpenShift Route, or Gateway API
HTTPRoute, with optional traffic splitting.
|===

Mutating and validating admission webhooks cover LogicPlatform, LogicFlowRuntime,
LogicFlowDefinition, and LogicFlowService. The operator's service account manages its child
resources. The gateway has a separate ServiceAccount and receives cluster-wide read permissions
through a platform-specific ClusterRoleBinding when enabled.

== Resource relationships

----
LogicPlatform (optional platform services)
  ├── Data Index Deployment + Service
  ├── Vector DaemonSet (optional)
  └── Workflow Gateway Deployment + Service (optional)
        └── Ingress or Route (optional)

LogicFlowRuntime
  ├── Deployment + Service (port 80 → container port 8080)
  └── LogicFlowDefinition(s) → one ConfigMap mount each
        └── LogicFlowService (optional ingress and traffic policy)
----

The Workflow Gateway can invoke a workflow directly through the runtime Service named by
`LogicFlowDefinition.spec.runtimeRef`. If a matching `LogicFlowService` publishes
`status.url`, the gateway uses that URL instead, preserving its external routing and traffic
policy. Gateway execution does not require Data Index; gateway instance queries do.

== Data and request paths

* Workflow execution: client → Workflow Gateway or LogicFlowService endpoint → runner.
* Optional workflow history: runner structured logs → Vector → PostgreSQL and Data Index GraphQL.
* Durable runtime state: runner → PostgreSQL, coordinated by Kubernetes Leases.

These are separate capabilities. Workflows can run without Data Index, Vector, or runtime
persistence. Enable the components required by your use case.

== Image versions

The operator build carries independent version settings for its own image, Workflow Gateway,
Data Index, and Quarkus Flow Runner: `{operator-version}`, `{workflow-gateway-version}`,
`{data-index-version}`, and `{quarkus-flow-runner-version}`, respectively. A LogicFlowRuntime with
no explicit image uses the runner version embedded in the current operator. LogicPlatform
admission defaults component image values when a platform is created; those values are stored in
its spec. Review and update pinned LogicPlatform images explicitly during upgrades. See
xref:deployment/production.adoc[Production Checklist].

== Prerequisites

* Kubernetes {k8s-min-version} or later.
* cert-manager for the admission webhook TLS certificate.
* An Ingress controller or OpenShift router if exposing services externally.
* PostgreSQL only for Data Index or durable runtime state.

Local KIND development additionally uses Docker, KIND, kubectl, and ingress-nginx. See
xref:deployment/kind-local.adoc[Local Development with KIND].
