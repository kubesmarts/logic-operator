= Workflow Definitions
:description: How LogicFlowDefinition represents an immutable, versioned workflow and loads it into a runtime.

A `LogicFlowDefinition` is a Kubernetes custom resource that holds the Serverless Workflow DSL body
for one version of a workflow. The operator reads this resource and writes the workflow YAML into the
ConfigMap shared by the target `LogicFlowRuntime`.

== Immutability

`LogicFlowDefinition` resources are *immutable once created*. The `spec` fields cannot be changed
after creation. This is enforced by a validating webhook.

Immutability is intentional: a workflow definition represents a specific, deployed version of a
workflow. Changing the definition in place would make it impossible to know what logic ran for
historical workflow instances. To deploy new logic, create a new `LogicFlowDefinition` with a
higher version.

[NOTE]
====
If you need to fix a bug in a deployed workflow, create a new `LogicFlowDefinition` with an
incremented patch version (e.g. `payment-processor-v1-0-1`) and update the `LogicFlowService`
to route traffic to the new version.
====

== Naming Convention

CR names follow the pattern `<workflow-name>-v<major>-<minor>-<patch>`. For example:

* `payment-processor-v1-0-0`
* `payment-processor-v1-0-1`
* `inventory-check-v2-3-0`

This convention makes the version immediately visible in `kubectl get logicflowdefinitions` output
and avoids ambiguity when multiple versions coexist.

== Workflow Identity: The Flow Name Annotation

The workflow name that the Quarkus Flow Runner uses to identify the workflow at runtime comes from
the annotation `org.kubesmarts.logic/flow-name`, *not* from the CR name.

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1alpha1
kind: LogicFlowDefinition
metadata:
  name: payment-processor-v1-0-0
  namespace: my-namespace
  annotations:
    org.kubesmarts.logic/flow-name: payment-processor   # <1>
spec:
  version: "1.0.0"
  serviceRef:
    name: payment-processor-svc
  definition:
    do:
      - processPayment:
          call: openapi
          with:
            document: ...
----
<1> The runtime uses `payment-processor` as the workflow's logical name. The CR name
`payment-processor-v1-0-0` is only a Kubernetes identifier.

This separation lets you version CR names without changing the workflow identity that clients and
Data Index use to query instances.

== Spec Fields

[cols="1,1,3", options="header"]
|===
| Field | Required | Description

| `spec.version`
| Yes
| Semantic version string (e.g. `"1.0.0"`). Used to construct the `document:` section of the
  Serverless Workflow YAML.

| `spec.serviceRef.name`
| Yes
| Name of the `LogicFlowService` CR that routes traffic for this workflow version.

| `spec.definition`
| Yes
| The Serverless Workflow DSL v1.0.0 body. Contains `do:`, `use:`, and other workflow-level keys.
  Do *not* include the `document:` section — the operator constructs it from metadata.
|===

== The `document:` Section Is Operator-Managed

The Serverless Workflow spec requires a `document:` section at the top of every workflow YAML.
Logic Operator generates this section automatically from the CR metadata so you do not repeat
yourself:

[source,yaml]
----
# Generated by the operator — do not write this yourself
document:
  dsl: "1.0.0"
  namespace: my-namespace
  name: payment-processor         # from annotation org.kubesmarts.logic/flow-name
  version: "1.0.0"                # from spec.version
----

Your `spec.definition` starts directly at the workflow body:

[source,yaml]
----
spec:
  definition:
    do:
      - processPayment:
          call: http
          with:
            method: post
            endpoint: https://payments.example.com/charge
    use:
      secrets:
        - payment-api-key
----

== Full Example

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1alpha1
kind: LogicFlowDefinition
metadata:
  name: payment-processor-v1-0-0
  namespace: checkout
  annotations:
    org.kubesmarts.logic/flow-name: payment-processor
spec:
  version: "1.0.0"
  serviceRef:
    name: payment-processor-svc
  definition:
    do:
      - validateCard:
          call: http
          with:
            method: post
            endpoint: https://validation.example.com/validate
            body:
              card: ${ .input.card }
      - chargeCard:
          call: http
          with:
            method: post
            endpoint: https://payments.example.com/charge
            body:
              amount: ${ .input.amount }
              token:  ${ .validateCard.token }
----

== How the Operator Loads the Definition

When the `LogicFlowDefinition` controller reconciles the CR, it:

1. Constructs the full Serverless Workflow YAML by prepending the generated `document:` section to
   `spec.definition`.
2. Writes the result into a dedicated ConfigMap named `lfd-<definition-name>` (e.g.
   `lfd-payment-processor-v1-0-0`).
3. The `LogicFlowRuntime` controller mounts each such ConfigMap as a directory under
   `/deployments/workflows/` in the runtime pods.

See xref:concepts/configmap-propagation.adoc[ConfigMap Hot-Reload] for details on how the runner
picks up the file.

== Deletion and Active Instances

Deletion of a `LogicFlowDefinition` is guarded to prevent removing a workflow that still has
running instances. In a future release the webhook will query Data Index for active instances and
block deletion if any are found. Until that integration is available, deletion proceeds without
the guard — exercise caution in production environments.
