= Workflow ConfigMap Propagation
:description: How Logic Operator materializes workflow documents as ConfigMaps mounted by runtime pods.

The `LogicFlowDefinition` controller creates one ConfigMap for each definition. The
`LogicFlowRuntime` controller mounts these ConfigMaps into its pods. Kubernetes propagates changes
to a mounted ConfigMap, but propagation of bytes does not by itself replace a workflow already
registered in the runner.

== One ConfigMap per definition

For example, `LogicFlowDefinition/payment-processor-v1-0-0` produces:

[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: lfd-payment-processor-v1-0-0
  namespace: checkout
data:
  payment-processor.yaml: |
    document:
      dsl: '1.0.0'
      namespace: checkout
      name: payment-processor
      version: '1.0.0'
    do:
      - processPayment:
          ...
----

The file key is `<workflow-name>.yaml`; the ConfigMap name is based on the Kubernetes CR name.
The operator mounts the ConfigMap as a directory at:

----
/deployments/workflows/lfd-payment-processor-v1-0-0/
----

Each definition has a separate volume and volume mount in the runtime Deployment.

== What changes trigger a rollout

[cols="2,1,3",options="header"]
|===
|Change |Deployment rollout? |Behavior

|Create a `LogicFlowDefinition`
|Yes
|A ConfigMap volume and mount are added to the runtime Deployment.

|Delete a `LogicFlowDefinition`
|Yes
|Its ConfigMap volume and mount are removed from the runtime Deployment.

|Update flow content in an existing `LogicFlowDefinition`
|No, by itself
|The controller updates the existing ConfigMap. The runner file watcher detects new workflow
files, but skips a workflow identity that is already registered. Restart runtime pods to load
changed content for the same workflow name and version.
|===

Kubernetes directory mounts update ConfigMap data eventually. The timing depends on kubelet's
sync loop and is separate from the runtime's file watcher. For a new workflow version, prefer a
new `LogicFlowDefinition` resource with the new version. New definition resources add a volume and
trigger a rolling update, ensuring all runtime pods load the definition at startup.

== Runtime file watcher

The runner image polls `/deployments/workflows` every five seconds by default to detect new
workflow files. It can register a newly appearing workflow identity without restarting the pod.
It does not replace an identity already present in that process. A ConfigMap edit that changes
the content of the same name/version therefore requires a runtime rollout to take effect.

Kubernetes ConfigMap volume projections use symlinks. The runner defaults
`followSymlinks` to false so it does not load duplicate files through both the symlinks and their
timestamped targets.

== Operational guidance

* Keep one released workflow version per `LogicFlowDefinition` resource.
* Create a new definition with an incremented version when changing released workflow logic.
* Use `LogicFlowService` to control traffic between versions when required; the gateway can also
  route to the definition's runtime directly.
* If you edit a definition without changing its identity, restart the runtime Deployment after
  the ConfigMap update.
