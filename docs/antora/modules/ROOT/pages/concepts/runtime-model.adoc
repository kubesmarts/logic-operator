= Runtime Model
:description: How Logic Operator runs shared Quarkus Flow Runner deployments and loads workflow definitions.

Logic Operator separates a workflow engine from the workflow documents it runs. A
`LogicFlowRuntime` manages a Quarkus Flow Runner Deployment and Service. One runtime can host
multiple `LogicFlowDefinition` resources, each of which supplies an OWS document through its own
ConfigMap.

== Shared runtime pools

Create a `LogicFlowRuntime` and reference it from one or more definitions:

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1
kind: LogicFlowRuntime
metadata:
  name: order-processing
spec:
  replicas: 2
----

The operator defaults the runtime to one replica and selects the runner image version embedded in
the operator. It uses the `minimal` image when persistence is omitted and the `standard` image
when PostgreSQL persistence is configured. The default runner version in this release is
`{quarkus-flow-runner-version}`.

== Resources created

[cols="1,3",options="header"]
|===
|Resource |Purpose

|Deployment
|Runs the Quarkus Flow Runner replicas.

|Service
|Exposes runner HTTP on port 80 and targets container port 8080.

|ConfigMaps and volume mounts
|One ConfigMap per linked `LogicFlowDefinition`, mounted into each runtime pod under
`/deployments/workflows/<configmap-name>/`.

|ServiceAccount, Leases, and RBAC
|Created when runtime persistence is configured; Leases coordinate durable execution across the
replica pool.
|===

These resources are created in the same namespace as the `LogicFlowRuntime`.

== Definition loading and updates

Each definition ConfigMap contains one `<workflow-name>.yaml` file. On startup the runner scans
`/deployments/workflows` and loads workflow definitions. Its file watcher can register a newly
appearing workflow identity, but it does not replace a workflow identity that is already loaded.
For a modified document with the same workflow name and version, restart the runtime pods to load
the new content. Creating or deleting a definition changes the Deployment's ConfigMap mounts and
causes a rollout.

For release management, use a new `LogicFlowDefinition` resource and workflow version for changed
logic, then direct traffic to the new definition through `LogicFlowService` or the gateway.

== Relationship between resources

----
LogicPlatform (optional shared components)
  └── Workflow Gateway (optional HTTP entry point)

LogicFlowRuntime (runner pool)
  ├── LogicFlowDefinition (workflow version)
  ├── LogicFlowDefinition (another workflow version)
  └── LogicFlowService (optional external routing and traffic policy)
----

A Workflow Gateway can route directly to the runtime Service using each definition's
`spec.runtimeRef`. When a matching `LogicFlowService` exists, the gateway uses its
`status.url`, preserving the service's ingress and traffic policy. See
xref:components/workflow-gateway.adoc[Workflow Gateway].

== Namespace scope

`LogicFlowRuntime`, `LogicFlowDefinition`, and `LogicFlowService` are namespaced resources. A
definition and its runtime must be in the same namespace. The operator's installation also
creates cluster-scoped CRDs and RBAC resources.
