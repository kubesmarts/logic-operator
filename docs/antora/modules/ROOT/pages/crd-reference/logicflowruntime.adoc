= LogicFlowRuntime
:description: Configure a Quarkus Flow Runner Deployment that can execute one or more workflow definitions.

`LogicFlowRuntime` represents a Quarkus Flow Runner Deployment and its Service. Multiple
`LogicFlowDefinition` resources can target the same runtime. Definitions are stored in separate
ConfigMaps and mounted into the runtime pods.

== API Version and Kind

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1
kind: LogicFlowRuntime
----

== Spec

`LogicFlowRuntime.spec` embeds the common runtime and application settings.

=== Image and pull policy

`image` optionally selects a runner image. When omitted, the operator uses the Quarkus Flow Runner
version built into the operator (`{quarkus-flow-runner-version}` in this release). It selects the `minimal` variant when
no persistence is configured and the `standard` variant when PostgreSQL persistence is present.
The minimal image is intended for in-memory execution; use the standard image for durable
workflow state.

`imagePullPolicy` defaults to `IfNotPresent` and accepts `Always`, `Never`, or `IfNotPresent`.

=== Replicas and autoscaling

`replicas` is defaulted to `1` by the LogicFlowRuntime admission webhook. The CRD exposes a
Kubernetes scale subresource, so an HPA should target the `LogicFlowRuntime` resource rather than
its generated Deployment. This allows the controller to reconcile the runtime and, when persistence
is enabled, its lease pool to the same replica count.

[source,yaml]
----
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello-runtime
spec:
  scaleTargetRef:
    apiVersion: logic.kubesmarts.org/v1
    kind: LogicFlowRuntime
    name: hello-runtime
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
----

Durable execution uses PostgreSQL-backed state and leases to coordinate instances across runner
replicas. Without persistence, workflow instance state is in memory; scaling or restarting pods
can interrupt active executions.

=== Resources and pod customization

`resources` configures the main container's requests and limits. `container` customizes the main
container, while `podTemplate` exposes pod-level fields and sidecars. Fields in `PodTemplateSpec`
are inline; for example, set `podTemplate.nodeSelector` or `podTemplate.containers` directly rather
than nesting them under `podTemplate.spec`.

[source,yaml]
----
spec:
  resources:
    requests:
      cpu: 250m
      memory: 512Mi
    limits:
      memory: 1Gi
  podTemplate:
    metadata:
      labels:
        team: payments
    nodeSelector:
      workload: workflows
    containers:
      - name: log-forwarder
        image: fluent/fluent-bit:3
----

The application container name and operator-managed labels/selectors are controlled by the
operator. `podTemplate` also supports scheduling constraints, volumes, image pull secrets,
init containers, sidecars, and a PodDisruptionBudget.

=== Persistence

`persistence.postgresql` configures the runtime database connection. The operator uses the
standard runner image, injects database settings, creates a ServiceAccount and RBAC for runtime
Leases, and reconciles one Lease per desired replica. The PostgreSQL Secret and Service must be
in the runtime namespace unless a Service namespace is specified. Choose a database schema that
does not overlap with Data Index.

[source,yaml]
----
spec:
  persistence:
    postgresql:
      secretRef:
        name: postgres-credentials
      serviceRef:
        name: postgres
        namespace: databases
        databaseName: logicflow
        databaseSchema: workflows
----

`serviceRef.port` is optional and defaults to `5432`; `databaseName` defaults to `logicflow`.
When `serviceRef.namespace` is omitted, the service name is used as a hostname and Kubernetes DNS
search resolves a same-namespace Service. Set `namespace` to build a fully qualified address for a
Service in another namespace. `secretRef.userKey` and `passwordKey` default to `POSTGRESQL_USER`
and `POSTGRESQL_PASSWORD`. Optional TLS settings are documented in the `PersistenceOptionsSpec`
source schema. For durable workflows, use the `standard` runner image if setting `image`
explicitly. `dbMigrationStrategy` is accepted by the schema but is not acted on by the current
operator; no migration Job is created by this setting.

=== Security

`security.type` configures runtime HTTP authentication: `NONE` (default), `API_KEY`, or `OIDC`.
Use an authenticated mode for production endpoints. API keys and OIDC client secrets are read
from Kubernetes Secrets in the runtime namespace.

[source,yaml]
----
spec:
  security:
    type: API_KEY
    apiKey:
      keys:
        - name: service-client
          secretRef:
            name: workflow-api-key
            key: value
          roles:
            - flow-invoker
----

API key roles are `flow-admin` and `flow-invoker`. OIDC settings include `authServerUrl`,
`clientId`, `clientSecret`, and optional `rolesClaim` (default `roles`).

=== Structured logging

`logging` optionally configures structured workflow logs. `enabled` defaults to `true` when the
field is provided, and payload inclusion defaults to `false`. Payload logging may expose sensitive
workflow data and should be enabled only when required. Vector collection is configured separately
on `LogicPlatform.spec.dataIndex.vector`.

[source,yaml]
----
spec:
  logging:
    enabled: true
    includeWorkflowPayloads: false
    includeTaskPayloads: false
----

== Status

The runtime reports:

[cols="1,3",options="header"]
|===
|Field |Meaning

|`observedGeneration`
|Most recently reconciled generation.

|`phase`
|`Pending`, `Ready`, or `Failed`, derived from runtime conditions and ready replicas.

|`replicas`, `readyReplicas`, `selector`
|Replica count, ready pod count, and selector used by the scale subresource.

|`deploymentRef`, `serviceRef`
|References to the managed Deployment and Service.

|`definitions`, `configMapRefs`
|Definitions and source ConfigMaps currently mounted by the runtime.

|`leaseReplicas`
|Desired Lease count when persistence is configured.

|`conditions`
|`DeploymentAvailable` and `ServiceReady`; `LeaseReady` is also reported with persistence.
|===

The runtime controller does not currently publish a condition named `Ready`. The CRD's `Reason`
kubectl print column looks for that condition and may therefore be blank; inspect `phase` and the
component conditions when diagnosing readiness.

== Reconciled resources

The controller creates a Deployment and Service named after the `LogicFlowRuntime`, plus one
volume and directory mount per linked `LogicFlowDefinition` ConfigMap. The Service exposes port
80 and targets runner container port 8080. With persistence configured, it also manages the
runtime ServiceAccount, Lease resources, and associated RBAC.

== Example

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1
kind: LogicFlowRuntime
metadata:
  name: hello-runtime
  namespace: default
spec: {}
----

The webhook sets one replica. The controller selects the minimal runner image at version
embedded in the operator build and creates `Deployment/hello-runtime` and `Service/hello-runtime`.
