= LogicFlowDefinition
:description: Define an Open Workflow Specification document and bind it to a LogicFlowRuntime.

`LogicFlowDefinition` stores one Open Workflow Specification (OWS) document and identifies the
`LogicFlowRuntime` that executes it. The controller validates and materializes the document as a
ConfigMap mounted by the runtime. A matching Workflow Gateway can route to the runtime directly;
`LogicFlowService` is optional.

== API Version and Kind

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1
kind: LogicFlowDefinition
----

== Spec

=== `runtimeRef`

Required reference to a `LogicFlowRuntime` in the same namespace. The target runtime is immutable
after creation. All versions of the same logical workflow in a namespace must use the same
runtime.

[source,yaml]
----
spec:
  runtimeRef:
    name: hello-runtime
----

=== `flow`

Required complete OWS document. Admission parses the document through the OWS SDK; the schema
preserves unknown OWS fields. The document must provide a workflow identity under `document`,
including `name` and `version`, and a valid workflow body.

The operator sets `document.namespace` to the Kubernetes namespace of the
`LogicFlowDefinition` when it serializes the flow into the runtime ConfigMap. The logical workflow
name is immutable on update. The version and other flow content can be updated in place, although
creating a new CR for each released version is a useful operational convention.

[source,yaml]
----
spec:
  flow:
    document:
      dsl: '1.0.0'
      namespace: examples
      name: hello-world
      version: '1.0.0'
    do:
      - greet:
          set:
            message: '${ "Hello, " + .name + "!" }'
----

== Reconciliation and status

For each definition, the controller:

. Parses the OWS document and extracts its logical name and version.
. Applies workflow identity labels and writes a ConfigMap named `lfd-<CR name>` in the same
  namespace.
. Stores the YAML flow document in a ConfigMap data key named `<workflow-name>.yaml`.
. Records the generated ConfigMap reference and workflow identity in status.

The `LogicFlowRuntime` controller mounts each definition ConfigMap under
`/deployments/workflows/<configmap-name>/`. Creating or deleting a definition changes the
runtime Deployment's volume mounts and triggers a rollout. Updating flow content updates the
existing ConfigMap. The runner's file watcher registers newly appearing workflow identities, but
does not replace one already loaded in a pod. Restart the runtime pods to load changed content for
the same workflow name and version.

`status.conditions` reports these controller states:

[cols="1,3",options="header"]
|===
|Condition |Meaning

|`FlowParsed`
|The OWS document parsed successfully.

|`ConfigMapReady`
|The generated ConfigMap was applied.

|`RuntimeRefValid`
|The referenced runtime exists.

|`RuntimeConsistent`
|Definitions for the same workflow identity use a consistent runtime.

|`Ready`
|The definition passed parsing and reference checks and its ConfigMap was reconciled.
|===

Other status fields include `observedGeneration`, `workflowName`, `workflowVersion`,
`workflowNamespace`, and `configMapRef`.

== Example

[source,yaml]
----
apiVersion: logic.kubesmarts.org/v1
kind: LogicFlowDefinition
metadata:
  name: hello-world-v1-0-0
  namespace: default
spec:
  runtimeRef:
    name: hello-runtime
  flow:
    document:
      dsl: '1.0.0'
      namespace: examples
      name: hello-world
      version: '1.0.0'
    do:
      - greet:
          set:
            message: '${ "Hi, " + .name + "!" }'
----

The CR name is a Kubernetes identifier and may include the workflow version. Routing uses the
identity parsed from the flow and stored on the resource, not the CR name.
